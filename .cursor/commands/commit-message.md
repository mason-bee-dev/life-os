# Generate commit message (life-os)

Follow **life-os** commit standards in:

@.cursor/rules/commit-message-convention.mdc

If that file is not in context, read `.cursor/rules/commit-message-convention.mdc` from this repo and apply it.

## What to do

1. Run in the project repo (this workspace): `git status`.
2. Then show the diff the user is about to commit:
   - If there are **staged** changes: `git diff --staged`
   - If **nothing** is staged: run `git diff`, say clearly that nothing is staged, and either draft from unstaged changes or ask the user to `git add` first—whichever is more helpful.
3. Produce **one** recommended Conventional Commit message (`type(scope): subject`) that matches the linked rule file. Add a short body with bullets only if it helps reviewers.
4. If the diff mixes unrelated changes, say so and suggest **splitting** into separate commits; give example subject lines for each.
5. Output the final message in a **single** fenced code block, ready to paste into `git commit` (multi-line body is OK). If you use bullets, put the first `-` on the line **immediately** after the subject (or after the last prose body line)—**no** blank line before the bullet list; use one blank line before footers only (`Fixes #…`, `BREAKING CHANGE:`).

**Hard requirement — no tool watermark or signature**

- Do **not** append `Co-authored-by:` (or similar) for Cursor / AI / assistants.
- Do **not** add lines like “Generated by…”, Cursor branding, emoji markers, or assistant links.
- The fenced block must contain **only** what belongs in `git commit` (subject, optional body, optional real footers like `Fixes #123` / `BREAKING CHANGE:` if the user asked for them)—never marketing or “here is your message” filler inside that block.

**Do not** run `git commit` unless the user explicitly asks you to execute the commit.
